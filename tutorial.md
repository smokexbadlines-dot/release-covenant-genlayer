# Tutorial: a challenge that survives the repair commit

Release Covenant demonstrates a useful GenLayer pattern: let validators interpret one small public claim, then let ordinary contract code enforce what that interpretation means. The example claim is that a release broke a documented compatibility promise. The contract does not ask an LLM to decide how much GEN anyone receives. It asks for a fixed label, and the payment rule stays in deterministic code.

Start with three public GitHub commits. The baseline commit should contain a concise promise in a small UTF-8 documentation file. The candidate release should contain a concise passage that clearly contradicts it. The repair commit should affirmatively show that the same promised behavior is restored. Keep each raw file below 24 KB. Use full 40-character SHAs rather than branch names or tags. These constraints make it possible for leader and validator nodes to fetch stable bytes independently.

In the app, connect a StudioNet wallet, open **Create**, enter the `owner/repo` path and the baseline and candidate commits, then choose ordered deadlines. The first close must be at least one hour in the future. Deploying creates a covenant in draft state. Add up to four promise statements, each with the path and exact quote at the baseline commit. Seal the covenant before the first challenge window ends. A sponsor can now send test GEN through `sponsor()`. The app keeps payable value separate from normal transaction status; the contract records the deposit under the sponsor's address.

A challenger chooses one promise and supplies a file path and exact quote from the candidate release. In `challenge()`, the contract validates input shape before entering the nondeterministic block. Both leader and validators fetch the pinned baseline and release files. They reject non-200 responses, empty bodies, oversized files, invalid UTF-8, and missing exact quotes as `INSUFFICIENT`. The prompt presents short excerpts around both quotes, warns that fetched text may contain instructions, and asks a narrow question: does the release passage clearly contradict the baseline promise? The only accepted labels are `BREAK`, `NO_BREAK`, and `INSUFFICIENT`.

The validator independently repeats the fetch and judgment, then compares the full returned label. That label is the only nondeterministic value allowed into contract state. If `BREAK` is accepted, the promise becomes `OPEN`, and the challenge path, quote, and commit are stored. The sponsor pool remains locked. A second attempt against an already open promise is rejected. A non-break or insufficient claim cannot block the release.

After the first close, a covenant with no open objections can settle in favor of the maintainer. If an objection is open, the maintainer has until the revision deadline to name one new release commit. `revise()` does not erase the objection. It changes that promise to `CARRIED`; unrelated promises become open to fresh challenges because the release commit changed. This is the core invariant: a new source version never inherits a clearance from an older source version.

Anyone can call `verify_repair()` for a carried objection, again with an exact quote at the new commit. This judgment is intentionally different from the first. `REPAIRED` requires positive evidence that the specific promised behavior is restored. Silence or an unrelated quote is `INSUFFICIENT`, even if it no longer says the behavior was removed. `STILL_BROKEN` marks the objection open. The second challenge window also permits fresh challenges against the revised release. If any objection remains `OPEN` or `CARRIED` at final close, settlement becomes `REFUND`.

The accounting path has no LLM discretion. Successful settlement credits the entire sponsored pool to the maintainer. Refund settlement lets each sponsor claim exactly their own recorded deposit. Both sides use `withdraw()` for an external transfer after finalization. A sponsorship sent too early or too late is credited directly back to its sender, so it cannot silently enter the release pool. The app reads balances from `LATEST_FINAL` state. It separately polls transaction IDs stored in the browser; an accepted transaction is shown as in progress until it finalizes with successful execution.

Run the direct tests with `python -m pytest tests/test_direct.py -q`. They cover a challenge carried through revision, positive repair, deadline refund, authorization, replay, a forged leader label, missing source, and late sponsorship. Those mocks check contract logic and validator comparison, but they cannot prove real model agreement or validator web access. Before recording proof, probe the chosen raw files on StudioNet, deploy from the exact source commit, and wait for finalized successful transactions. Put their IDs and state readbacks in `deploy/proof.json`; `pnpm verify:proof` then rechecks them without writing to the network.
